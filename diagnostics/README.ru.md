Официальная база: публичный тег `1.4.0.2` репозитория `Valkirie/HandheldCompanion`, коммит `0a0a13b937ed987a131a0729226a03de374e7d91` (релиз «1.4.0.2 - Motion controls, profiles & ONEXPLAYER 3», 2026-11-07). Версия в `.csproj` не менялась. Ветка форка `main` не инструментировалась.

Исполняемый файл не запускался. Проверки внутри FSE и на Windows не было.

На Linux фактически выполнено:

- Кросс-компиляция `dotnet build HandheldCompanion.sln -c Debug -p:Platform=x64 -p:EnableWindowsTargeting=true` (SDK 10.0.404) дошла до 0 ошибок только после локальной подстановки reference assemblies .NET Framework 4.8 и временного обхода cmd-событий PreBuild/PostBuild. ## Сборка

На Windows, из корня дерева на этом коммите:

```
dotnet build HandheldCompanion.sln -c Release
```

Исходники журнала подключены к приложению напрямую, отдельная библиотека для сборки HC не нужна. Переносимые тесты, если установлен .NET 8:

```
dotnet test diagnostics/FseInputDiag.Tests/FseInputDiag.Tests.csproj
```

Готовый `HandheldCompanion.exe` заменяет обычный запуск. Этот патч сам ничего не устанавливает и не перезапускает приложение.

Обычный Release по-прежнему берёт `HandheldCompanion/RELEASE.manifest`: `requireAdministrator` и `uiAccess="true"`. Это не менялось.

Отдельный диагностический манифест `diagnostics/DIAGNOSTIC.no-uiaccess.manifest` включается только явно:

```
dotnet build HandheldCompanion.sln -c Release -p:DiagnosticNoUiAccess=true
```

В нём остаётся `requireAdministrator`, а `uiAccess="false"`. Это обычное приложение с запросом UAC, без привилегии UIAccess и без обхода проверок Windows. Без свойства `-p:DiagnosticNoUiAccess=true` этот манифест не используется. Подпись, политики, сертификаты и установленная копия этой настройкой не меняются.

Такой пакет не равен штатному HC. Совпадение phenotype не доказывает первопричину штатной сборки: у неё другой флаг UIAccess. Отличие относится только к режиму no-uiaccess. Уровень integrity FSE не измерялся, совместимость с FSE по IL не заявляется. Windows и FSE этим деревом не запускались.

Критерий будущего эксперимента, если пакет вообще стартует: сначала тот же phenotype. OXP через HC есть вне FSE и нет в FSE. Switch через тот же virtual output есть в FSE.

## Включение

Захват выключен, пока нет файла

`%LocalAppData%\HandheldCompanion\fse-input-diag.arm`

Файл можно создать в Проводнике. Первая строка — необязательная задержка в секундах, например `12`. Пустой файл означает 12 секунд. Допустимо 3–20; иные числа обрезаются до этого диапазона. Текст файла в журнал не копируется.

После появления файла приложение ждёт эту задержку и только потом пишет 30 секунд. За это время можно вернуться в FSE. Окон, тостов и глобальных горячих клавиш нет. Повторное создание файла во время ожидания или захвата не продлевает окно. Смена источника тоже не продлевает. Новый захват возможен только после завершения предыдущего.

Результат, каждый раз с нуля:

- `%LocalAppData%\HandheldCompanion\fse-input-diag.jsonl`
- `%LocalAppData%\HandheldCompanion\fse-input-diag.summary.txt`
- `%LocalAppData%\HandheldCompanion\fse-input-diag.status.txt`

Заголовок журнала версии 2 содержит `sid` и абсолютный `utc` старта захвата. Подвал содержит `sid` и `utc` конца. Файл статуса — несколько строк `arm=accepted`, `arm=rejected` с `reason` (`busy`, `writer_alive`, `error`) или `arm=finished` / `arm=open_failed`. В нём нет путей, имён и заголовков окон. Пока там нет нового `sid`, повторный захват не начался: старый JSONL мог остаться от предыдущего сеанса. Новый сеанс не продлевает уже закрытые 30 секунд.

Полный путь содержит имя пользователя, поэтому в сами файлы он не пишется.

## Формат

JSONL, UTF-8. У каждого кадра один `f` и одно `ms` от монотонного старта захвата.

- `raw` — источник после уже существующего чтения бэкенда: `be` (`xinput` или `sdl`), `alias` (`oxp`, `switch`, `xinput`, `sdl`), `ui` (индекс, которым читали), `pnpUi` (индекс PnP), `vid`, `pid`, `tail` (последний кусок instance id, только буквы и цифры), `inst` (FNV-1a 32 по UTF-16), `virt`, `dummy`, `xinput`, `vidPidMatch` (виртуальный и VID/PID совпали с текущей виртуальной целью), `sdlType`, `res`, `err` (HRESULT, без текста), `skip`, кнопки и оси.
- `map` — состояние после раскладки (`btn`, оси) и то, что реально ушло в виртуальный вызов (`outBtn`, `out*`). Флаги: `publishLive`, `halt` (`none`, `no_target`, `null_state`, `broadcast`), `mute`, `listen`, `focus` (фокус UI HC), `fgPid`, `fg` (только имя exe), `hid`, `mode`, `vVid`, `vPid`, `vConn`.
- `send` — решение: `not_reached`, `listening`, `sleep`, `unchanged`, `null_target`, `disconnected`, `sent`, `send_error`.

`res=ok` значит, что существующее чтение вернуло состояние. Кнопки при другом `res` новому чтению не соответствуют. Нулевые оси при `res=ok` — это успешное чтение нулей, а не пропущенный вызов.

Пределы, их нельзя поднять файлом: 30000 мс, 12000 записей, 3145728 байт, очередь 512. Лишнее считается в `queueDrops`, `sampleDrops`, `byteDrops` и в summary. Хвост файла может оборваться на границе кадра.

## Как читать оба бэкенда

OXP идёт как `be=xinput`, `alias=oxp`. Switch Pro USB идёт как `be=sdl`, `alias=switch`. Сравнивать строки с одним `f`.

- `raw.res` = `skipped`, `failed`, `null` или `missing`: до раскладки чтение не состоялось. `skip=disconnected` — SDL не видит устройство; `unplugged` — контроллер не выбран целью; `err` — код исключения XInput.
- `raw.res=ok`, кнопки/оси нулевые, а физически они нажаты: чтение прошло, но значения пустые. Смотреть `ui`, `pnpUi`, `virt`, `tail`, `inst`, `vidPidMatch`. Физический OXP и виртуальный Xbox 360 имеют один VID/PID `1118/654`; их различают `virt` и `tail` (`0123456789` и `296013F`). Совпадение `virt=true` и `vidPidMatch=true` показывает, что выбранный источник — виртуальное устройство. Это факт идентичности, не вывод о причине.
- `raw` ненулевой, `map.btn` пустой: значения сняты после чтения и потеряны на раскладке.
- `map.btn` ненулевой, `mute=true`, `outBtn` пустой: после раскладки сработал mute фокуса UI HC. `focus` — отдельный флаг того же фокуса.
- `listen=true` и `send=listening`: виртуальная отправка не вызывалась из-за прослушивания хоткея.
- `send=unchanged`: гейт «без значимого изменения».
- `send=disconnected` или `null_target`: цель не приняла отправку. `send=sent` значит, что существующий `UpdateInputs` дошёл до `SendInput`. `send_error` — исключение внутри уже существующего catch.
- `publishLive=false`: в конвейер отдан нейтральный кадр, потому что цель не dummy и не готова/не подключена, даже если `raw` успел прочитаться.
- `halt=broadcast` / `no_target` / `null_state`: до раскладки и отправки кадр вышел по уже существующей ветке.

Одинаковые поля пишутся для XInput и SDL. Отдельного внешнего XInput-зонда патч не добавляет и все четыре индекса сам не опрашивает.

Файл локальный, сеть не используется. Нет заголовков окон, имён пользователей, клавиатуры, вводимого текста и секретов. Есть PID и имя exe переднего плана, кнопки и оси геймпада, VID/PID, короткий хвост instance id и его хеш.
